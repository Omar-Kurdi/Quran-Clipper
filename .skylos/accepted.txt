# Pre-existing findings that `skylos baseline` cannot record.
#
# `--baseline` captures most of what this repo already had, but three rule
# families are re-reported on every run no matter what is in the baseline.
# The ones below were all present before the gate existed, they are listed
# here individually rather than waved through by rule, and anything NEW --
# including a new occurrence of these same rules anywhere else -- still blocks.
#
# Format: <file>  <RULE-ID>  <how many of that rule that file is allowed>.
# Comments and blank lines are ignored. Read by scripts/skylos-accepted.py,
# which explains why the count is the key and what that trades away.
#
# There are deliberately no line numbers. They were the key until the gate went
# red on a change that introduced nothing: deleting dead code moved every
# finding below it, and a file that reds on unrelated edits is a file people
# learn to wave through. A count cannot drift. Raising one is still the thing
# this gate exists to stop -- fix the finding, or bring it up.

# Two parameters kept for signature symmetry with the other aligner entry
# points. Real findings, and worth cleaning up -- but removing a parameter is
# an application change, which the verification work is deliberately not doing.
asr-service/app/align.py  SKY-U006  2

# False positives. Both are config files loaded by tooling rather than imported
# by application code -- drizzle-kit reads one, PostCSS the other -- so "not
# imported by any other file" is true and means nothing. Deleting either breaks
# the build.
drizzle.config.ts  SKY-E003  1
postcss.config.mjs  SKY-E003  1

# SKY-D260, six findings in four files that predate this gate and that no
# verification change has touched. `skylos baseline` captures none of this rule
# family, the same way it captures no SKY-U006 or SKY-E003, so they are counted
# here instead. Accepted as written, not as a rule: SKY-D260 in any other file
# still blocks, and that is the point -- the rule is a reasonable one and a
# genuine planted instruction elsewhere should stop a build.
#
# The Arabic pair are U+200E, the left-to-right mark. Arabic is bidirectional
# text, and the mark is how a Latin word or a number is kept from flipping the
# run around it. It is invisible because that is its entire job. Removing them
# would corrupt the rendering of the very documentation they appear in.
README.ar.md  SKY-D260  2
docs/ALIGNMENT.ar.md  SKY-D260  2

# The other two are ordinary prose and an ordinary docstring, flagged for
# describing how forced alignment differs from free decoding. Both sentences are
# load-bearing explanations of the algorithm. They are not quoted here: the rule
# matches on the wording, so repeating it in this file makes this file a finding
# too -- which is exactly what happened on the first attempt.
docs/ALIGNMENT.md  SKY-D260  1
asr-service/app/align.py  SKY-D260  1
